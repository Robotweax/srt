# Integrate Robotweax SRT

1. Inspect the application before choosing a build. Record target OS, architecture, package/deployment format and build system, current headers and SRT provider, executable or loading plugin, peer products and exact versions, role (Caller/Listener/Rendezvous), independent media direction, Live/Message or File/Stream mode, and required security. Record codecs/selected tracks or file contract, independent UDP channels versus accepted sockets, offered rate and stream count, latency/loss targets, CPU quota/affinity and any shared bottleneck. Mark unknowns and verify ones that affect the choice.
2. Pin the Robotweax release, exact artifact or source revision, ABI, architecture, crypto backend and feature flags before changing dependencies. Use [integration and provenance](references/integration.md) to select the native or application adapter path. Follow the selected tag's own docs, headers, examples, harnesses and results. Gather evidence of the provider bound in the running application, including plugins and static archives. API version or a successful wire connection alone cannot establish product identity.
3. Pick a documented common profile for the exact peers and required security. Use [socket and security configuration](references/socket-profile.md) to set options in order, read back meaningful settings, and check units. Gate FEC, groups, AES-GCM and Robotweax peer authentication independently, including combinations. If a requirement lacks a verified common profile, report the missing or unsupported combination and ask the customer to choose a qualified peer/profile that preserves the requirement or defer deployment. Do not retry by weakening security. A clear test is a separate synthetic scenario and does not qualify encryption.
4. Run and report [interoperability qualification](references/qualification.md) for the actual builds before calling the integration ready. Test both roles and media directions where supported, decode picture and selected audio or compare file hashes, then exercise reconnect and normal shutdown. Preserve failed and unsupported runs and mark unavailable targets NOT RUN.
5. For scheduling advice, use the [shard decision guide](references/shards.md). Start from the tagged defaults and treat topology and measured target headroom as inputs to sizing. Keep Live priority explicit when File and Live compete.
6. Hand back the dependency/config changes, exact revisions and commands, provider proof, matrix results, and outstanding decisions with owners. Label each recommendation **released and verified** for its exact evidenced profile, **documented but untested for this combination**, or **experimental / unsupported**. Keep the release's published qualification separate from fresh customer test results.

For a reusable loopback check with generated media, use [smoke instructions](references/qualification.md#local-clear-live-smoke). The helper can also check an explicitly observed artifact against a trusted manifest.
